# `end_effector.shm/1` — an end effector served by its own process

**Contract version:** 1 (`schema_version` 1). **Transport:** iceoryx2
`=0.9.3`. **Byte layout:** `1.layout.json` beside this file, which is
normative for every offset, size, code and service setting; the tables below
mirror it and a test fails when they drift apart. **Rust definitions:** crate
`d1fw-ee-shm-contract`. **Daemon side:** `d1-firmwared`'s shared-memory
driver; for a provider's tests, `Host` of crate `d1fw-ee-harness` applies
the same rules. **Provider SDK (Rust):** crate `d1fw-ee-provider`.

This contract lets an end effector be driven by a process of its own — a
**provider** — while `d1-firmwared` (the **daemon**) serves it to every
client through its unchanged REST and WebSocket resource
`/v1/end_effectors/{a|b}`. The provider owns everything device-specific (its
bus, its protocol, its probe, its calibration); the daemon sees only what
this contract carries: a descriptor, the neutral state and ticks, an opaque
`detail`, and two request lanes. The daemon keeps the safety duties: command
validation, the joint-command timestamp rule, the command ceiling, the
soft-kill latch and the stop.

It is the one boundary through which the daemon serves an end effector it
does not build in, whatever carries the device: an end effector driven over
ROS 2 reaches the daemon through a bridge process that is a provider of this
contract, and one on the arm's flange CAN channel, which only the daemon
reaches, talks to its device through the daemon's relay of that channel, the
sibling contract `flange_bus.shm/1` (`spec/flange_bus.shm/1.md`).

The key words MUST, MUST NOT, SHOULD and MAY are to be read as in RFC 2119.

## 1. Transport and root

1. Every participant MUST be built against iceoryx2 `0.9.3` exactly (the Rust
   crate, or the Python package of the same version). iceoryx2 does not
   guarantee shared-memory compatibility across releases.
2. Every participant MUST build its iceoryx2 node from iceoryx2's default
   configuration with exactly two values changed, and MUST NOT use a
   per-account or system-wide iceoryx2 configuration file:

   | setting | value on a robot | daemon configuration key |
   | --- | --- | --- |
   | `global.root-path` | `/run/d1-firmwared/iceoryx2/` | `[end_effector] shm_root_path` |
   | `global.prefix` | `omakase_ee_` | `[end_effector] shm_prefix` |

   The root lies inside the daemon's runtime directory (`/run/d1-firmwared`,
   created by systemd for the daemon's unit, mode 0750, kept across daemon
   restarts until the host reboots). The prefix keeps these resources apart
   from every other iceoryx2 user's in `/dev/shm`.
3. iceoryx2 0.9.3 creates every segment, socket and lock file readable and
   writable by its owner only. A provider MUST therefore run as the account
   the daemon runs as (`User=` of `d1-firmwared.service`; `doraemon` on a D1
   provisioned by `d1-host`). A provider unit MUST NOT use `DynamicUser=`,
   `PrivateIPC=`, `PrivateDevices=` or `PrivateUsers=` (each separates its
   `/dev/shm` or its account from the daemon's); with `ProtectSystem=strict`
   it needs `ReadWritePaths=/run/d1-firmwared/iceoryx2`. This is a limitation
   of version 1: iceoryx2 0.9.3 sets each resource's mode after creating it
   from a compile-time constant (owner only) and offers no configuration of
   it, so neither a umask nor a shared group can widen it. A provider whose
   program lives in a developer's own home still runs as the daemon's
   account; the daemon's package ships the template unit
   `d1-firmwared-ee-provider@.service` for that (one instance per side, its
   command in `/etc/d1-firmwared/ee-provider/<side>.env`).
4. A provider that starts before the daemon finds no `/run/d1-firmwared`
   and SHOULD retry creating its node until it exists; the daemon creates the
   root directory when it opens its services.

## 2. Services

A side is bound by a **base** name: `omakase/ee/<side>` unless
`[end_effector.<side>] shm_service` names another. A base is 1 to 128 bytes
of `a-z`, `0-9`, `_`, `-`, `.` and `/`, with no empty segment and no leading
or trailing `/`. The daemon and the provider MUST open every service with
the settings below (either may create it first, and iceoryx2 refuses an open
whose settings are incompatible with the creator's). Every service payload
is one fixed-size message; every user header is `()`.

| service | pattern | payload | writer | history | buffer | safe overflow | max writers | max readers |
| --- | --- | --- | --- | ---: | ---: | --- | ---: | ---: |
| `<base>/descriptor` | pub/sub | `Descriptor` | provider | 1 | 2 | true | 1 | 4 |
| `<base>/heartbeat` | pub/sub | `Heartbeat` | provider | 1 | 2 | true | 1 | 4 |
| `<base>/state` | pub/sub | `State` | provider | 1 | 2 | true | 1 | 4 |
| `<base>/tick` | pub/sub | `Tick` | provider | 0 | 64 | true | 1 | 4 |
| `<base>/joints` | pub/sub | `JointsCommand` | daemon | 0 | 4 | true | 1 | 2 |
| `<base>/control` | pub/sub | `Control` | daemon | 1 | 2 | true | 1 | 4 |
| `<base>/command` | req/resp | `CommandRequest` → `CommandResponse` | server: provider | max_servers 1, max_clients 2, max_active_requests_per_client 4, max_response_buffer_size 2, no safe overflow either way |
| `<base>/fault` | req/resp | `FaultRequest` → `FaultResponse` | server: provider | max_servers 1, max_clients 2, max_active_requests_per_client 4, max_response_buffer_size 2, no safe overflow either way |

Every topic admits exactly one writer, so a second provider (or a second
daemon) cannot bind a side that already has one: creating its publisher
fails. A provider killed without cleanup leaves its resources behind;
iceoryx2 removes a dead node's resources when the next node is created or
the service is next opened, so a restarted provider binds the side again.

## 3. Messages

Every message is a C struct (`#[repr(C)]`), little-endian, with explicit
`reserved` fields and no implicit padding (its fields tile it from offset 0
to its size). Conventions:

- **Strings** are UTF-8, NUL-padded to the field's capacity: no NUL inside
  the text, and only NUL after it. A receiver refuses anything else.
- **An optional `f64`** is NaN when absent; any other value MUST be finite.
- **A `reserved` field** is written as 0 and ignored on receipt.
- **A count** (`joint_count`, `set_extra_count`, `*_len`) MUST NOT exceed
  its field's capacity; entries beyond it are ignored.
- **A flag word** MUST NOT set a bit schema 1 does not define; a receiver
  refuses the message. (A new bit is a new contract version.)
- **The iceoryx2 type name** of each message carries the major version
  (`omakase_ee_v1_*`), so a participant built against another major cannot
  open the services at all.

### 3.1 Header

Every message starts with a `Header`:

- `schema_version` MUST be `1`. A receiver MUST refuse a message with any
  other value, whatever its layout.
- `instance_id` is a random non-zero value the sender draws once per process
  start. A receiver tells a restarted peer by it.
- `seq` increases strictly per sender and service, from 1.
- `mono_ns` is `CLOCK_MONOTONIC` in nanoseconds when the message was
  produced. Both sides run on one host, so the daemon and the provider read
  the same clock.

### 3.3 Codes and bits

| field | values |
| --- | --- |
| `Joint.unit` | `0` rad, `1` fraction of the axis's range (`0.0` … `1.0`) |
| `Descriptor.capabilities` | bit 0 `openness`, 1 `joints`, 2 `stroke_completion`, 3 `grip_torque`, 4 `contact_sensing`, 5 `clear_fault`, 6 `registers`, 7 `ticks`, 8 `joint_velocity`, 9 `joint_effort` |
| `Descriptor.tool_declared` | `0` no tool declared (`tool` is zero and ignored), `1` `tool` is declared |
| `Descriptor.grip_presets` | bit 0 `soft`, 1 `firm`, 2 `strong` |
| `Descriptor.force_sensing` | `0` none, `1` estimated, `2` measured |
| `State.flags` | bit 0 `live`, 1 `tracking`, 2 holding known, 3 holding, 4 contact known, 5 contact, 6 cap_reached known, 7 cap_reached, 8 detail dropped |
| `Tick.phase` | `0` idle, `1` closing, `2` opening, `3` hold |
| `Tick.flags` | bit 0 `commanded` valid, 1 `effort` valid |
| `CommandRequest.op` | `1` set, `2` stop |
| `CommandRequest.flags` | bit 0 wait, 1 `grip` valid, 2 `torque_nm` valid |
| `CommandRequest.grip` | `0` soft, `1` firm, `2` strong |
| `FaultRequest.op` | `1` clear_fault, `2` registers |
| `status` (responses) | `0` ok, `1` refused, `2` unprocessable, `3` unavailable, `4` device, `5` timeout, `6` stale_target, `7` invalid |

A tri-state (`holding`, `contact`, `cap_reached`) is its "known" bit and its
value bit: known and clear is `false`, unknown is `null`.

### 3.4 What each message means

**`Descriptor`** (provider, latched, republished at least every 500 ms):
what the provider drives. `generation` starts at 1 and rises whenever the
declaration changes; the one change a running daemon takes is `node_id`
from `-1` to a value (§5). `driver` and `model` are 1 to 64 bytes.
`detail_schema` is the schema id the state's `detail` follows, of the form
`<id>/<major>` (an `id` without `/`, then a decimal `major` from 1 without
leading zeros, at most 64 bytes, for example `acme.report/1`), or empty when
the provider publishes no detail. The id is the provider's own: there is no
class label in this contract, and a client decides what the device is from
its capabilities and joint count. `node_id` is the bus address the provider found its device at, or
`-1` while it has not found it (a provider that probes for its device
announces itself before the device answers, and redeclares with the address
once it does). `joints` are the joints of the `joints` command mode in command order:
names 1 to 32 bytes and unique, limits finite with `min < max`; the
`joints` capability needs at least one. `max_command_hz` is the
vendor-rated ceiling on commands (`0`: none published; otherwise 1 to
10000). `set_timeout_ms` is how long a `set` with wait may take (`0`: 10000;
otherwise 1 to 60000). `set_extra` lists the keys `set` accepts in its
`extra` object (at most 8, 1 to 32 bytes, unique).

`tool` (valid when `tool_declared` is 1) is what the arm controller must
compensate for while this end effector is on the flange, in the flange
frame and in the units and order of `POST /v1/arm/{side}/tool`: `mass_kg`
(kilograms, finite and not negative), `com_mm` (the centre of mass,
millimetres, XYZ), `inertia` (kg·m² about the centre of mass, `Ixx, Ixy,
Ixz, Iyy, Iyz, Izz`), `tcp_xyz_mm` (the tool centre point, millimetres,
XYZ) and `tcp_rpy_deg` (its rotation, degrees, roll/pitch/yaw in XYZ order);
every value finite. A provider that declares no tool leaves the side's arm
registration to its integrator (`POST /v1/arm/{side}/tool`).

`guard_model` is the id of the collision envelope the daemon's arm guard
should check this end effector with (for example `d1/parallel_gripper`, the
D1's stock parallel gripper), 1 to 64 bytes, or empty for none declared. The
guard checks the end effector as a set of capsules on the flange, and it
carries the envelopes compiled into the daemon only: this contract carries
an id, never geometry. An id the guard does not know (or none) leaves the
side on the guard's default envelope, and the daemon reports the envelope it
applied (§5).

**`Heartbeat`** (provider, at least every 100 ms): the provider is alive and
declares `descriptor_generation`. `state_period_ms` is informative.

**`State`** (provider, on its state period, at most 1 s): the neutral state,
in terms of `descriptor_generation`. `tracking` (flag bit 1) means a
streamed target has been taken and not yet reached: a provider clears it
once the end effector has arrived and only holds, including when it stopped
short on an object, and re-sending the same target does not set it again.
The daemon counts a side reporting `tracking` as moving. `joint_count` is the descriptor's joint
count, or 0 when there is no reading. `openness` is in `[0, 1]` or NaN.
`velocity` and `effort` carry, for each of the `joint_count` joints, the
joint's measured velocity (in the joint's unit per second) and the effort
its actuator reports (newton-metres for a rotary actuator, newtons for a
linear one), or NaN for a joint whose value is not known; ±infinity is
refused. A provider that does not declare `joint_velocity` (or
`joint_effort`) writes NaN throughout that array, and the daemon reads it
only with the capability declared.
`detail` is the UTF-8 JSON object `{"schema", "data"}` (`detail_len`
bytes, at most 8192; no other key): the provider's own full report, opaque
to the daemon and read by a client only under a schema id it knows. Its
`schema` MUST equal the descriptor's `detail_schema`; the daemon publishes
no detail for a state whose `schema` differs, or whose descriptor declares
none.
A provider whose detail does not fit MUST send none and set bit 8, never a
truncated one. A provider that cannot read its device publishes a state with
no reading (`joint_count` 0, `live` clear) and the reason in `fault`.

**`Tick`** (provider, optional, with the `ticks` capability): one
control-loop tick, the input of the daemon's command-versus-measured
telemetry. `tick_seq` increases strictly; `timestamp_us` is wall-clock
microseconds; `commanded` and `effort` are valid with their flag bits and
then have `joint_count` entries.

**`JointsCommand`** (daemon): one set of streamed joint targets, already
validated by the daemon (count, finiteness, limits) and ordered by the
client's wall-clock `timestamp_us` (strictly increasing per side; the daemon
refuses an older one with 409 `stale`). `target_instance_id` and
`descriptor_generation` name what the targets were validated against.

**`Control`** (daemon, latched, every 100 ms): the daemon is alive, and
`stop_generation` rises by one on every stop the daemon issues on this side.

**`CommandRequest` / `CommandResponse`** (daemon → provider): `set` (an
openness in `[0, 1]`, wait, grip, torque, `extra` as a JSON object of at
most 1024 bytes) or `stop`. `start_by_mono_ns` is the request's issue time
plus 250 ms. The response carries a status and, unless `ok`, a message of
at most 256 bytes.

**`FaultRequest` / `FaultResponse`** (daemon → provider): `clear_fault`, or
`registers` with `ids` (a JSON array of strings, `ids_len` 0 for the
provider's default set). The response body (`body_len` bytes, at most
16384) is UTF-8 JSON: `{"ok", "fault", "details"}` for a clear and
`{"entries": [{"id", "name", "value", "details"}], "details"}` for a dump —
the REST bodies of `POST /v1/end_effectors/{side}/clear_fault` and
`GET /v1/end_effectors/{side}/registers` — with every `details` opaque. A
body that does not fit is answered `device` with a message saying so.

## 4. Rules a provider MUST follow

1. Validate its own declaration before serving it; the daemon refuses a
   malformed one and says why in the side's `error`.
2. Publish its heartbeat at least every 100 ms, its descriptor at least
   every 500 ms, and its state at least every second, on its own schedule,
   not only after a command.
3. Execute a `set` only when `target_instance_id` is its own instance,
   `descriptor_generation` its current generation, and `CLOCK_MONOTONIC` has
   not passed `start_by_mono_ns`; otherwise answer `stale_target` without
   executing it. Refuse a grip, torque or `extra` key it did not declare
   (`unprocessable`), and an openness without the `openness` capability
   (`refused`). The `set`s that need no `openness` capability are the keyed
   ones, a hold (rule 10) and a home (rule 11): a `set` whose `extra` names
   the key `hold` or `home` is that verb, and it is accepted only from a
   provider that lists the key in `set_extra` (otherwise `refused`), and
   only as exactly `{"hold": true}` or `{"home": true}` with no wait, grip
   or torque (otherwise `unprocessable`); its `openness` is ignored (the
   daemon sends `0.0`).
4. Execute a `stop` whatever it is addressed to and however late it
   arrives. A stop takes the actuators' authority away and MUST NOT open:
   an end effector holding an object must not drop it. A stop MUST be
   idempotent.
5. Stop when the daemon's `stop_generation` rises. The first value seen
   from a daemon instance (after the provider starts, or after the daemon
   restarts) is the baseline, never a stop to act on.
6. Take only the newest `joints` sample per wake-up, and drop one whose
   header `mono_ns` is more than 200 ms old, one addressed to another
   instance or generation, and one outside its declared limits. Joint
   targets never wait for motion.
7. While the daemon's `control` is absent (no sample for 500 ms), keep
   holding what it holds and start no motion of its own.
8. Answer every request; the daemon reports an unanswered `set` as
   `timeout` after `set_timeout_ms` + 500 ms (2 s without wait), a `stop`
   after 2 s, and a `clear_fault` or `registers` after 60 s.
9. Change a declaration only in `node_id`, from `-1` to the address its
   device answered at (§5); any other change is refused until the daemon
   restarts.
10. Treat a hold — a `set` with `extra` `{"hold": true}`, from a provider
    that lists `hold` in `set_extra` — as "keep the actuators holding where
    they are now, with no command watchdog of your own, until the next
    command". Where they are now is the last set-point the provider's own
    control sent, not an unreached target (a hold never advances towards
    one) and not the measured pose (a grasp held at the measured pose
    exerts no force). A watchdog that ends a hold when no newer `joints`
    target arrives is disarmed until the next `joints` target (which arms
    it again), `set`, `stop`, a fault or a cleared fault. A hold gives no
    authority back to actuators that are off: on a stopped or disabled end
    effector it changes nothing and is answered `ok`. A held end effector is
    not `tracking`. Rule 7 applies to it as to any hold. A provider without
    a watchdog of its own, whose actuators keep their last command anyway,
    need not list `hold`; the daemon then answers a hold for that side
    without sending it (§5).
11. Treat a home — a `set` with `extra` `{"home": true}`, from a provider
    that lists `home` in `set_extra` — as "drive to your own home pose
    through your normal control, then hold there". The home pose is the
    provider's own and documented with it. The motion replaces any streamed
    target and goes through the provider's ordinary limits (step limiting,
    effort limits); actuators that are off are brought on as a first
    target would bring them. The state reports `tracking` until the end
    effector has arrived, and from then on it holds as after a hold (rule
    10) until the next `joints` target, `set`, `stop`, a fault or a cleared
    fault. The answer comes once the motion has started, not when it ends.

A provider should publish the state a `set`, `stop` or `clear_fault` left
before it answers the request, so that a state read after the answer is not
older than the command (the Rust SDK does, with `Provider::settled`). The
daemon delivers an answer only after taking the provider's topics again.

## 5. What the daemon does

**Acceptance.** The daemon accepts the first valid descriptor announced on a
side and keeps it for its lifetime. A provider that restarts and announces
the same declaration is taken back at once; one that announces a different
declaration is refused until the daemon restarts, so a client never sees
joints, limits or capabilities change under it. The bus address is the one
exception: a declaration equal in everything but `node_id` is taken when
`node_id` goes from `-1` to a value, once (the side's REST descriptor
reports that value from then on), and when a restarted provider announces
`-1` again (it has not found the device yet; the value is kept); a value
other than the one taken is refused until the daemon restarts. The state
kept from before a new generation is dropped. When the side's
configuration names `model`, a provider announcing another model is refused.
A descriptor of another schema version, or one that breaks a rule of §3, is
refused. Each refusal is logged once and reported in the side's `error`.

**The tool.** When the daemon accepts a descriptor that declares a `tool`,
it registers exactly those values on the side's arm (the side's
`GET /v1/arm/{side}/tool` then reads `source: "config"`, named by the
daemon's catalog id when the tool is exactly a catalog entry — the stock
gripper's `d1/parallel_gripper` — and by the descriptor's `model`
otherwise), once, and again after every arm recover. A tool a client registered with
`POST /v1/arm/{side}/tool` outranks it until the daemon restarts: the
daemon then registers nothing. A descriptor without a tool registers
nothing, and the side's REST descriptor reads `tool: null`. Because a
declaration is kept for the daemon's lifetime, a provider that restarts
with a different tool is refused like any other changed declaration.

**The guard envelope.** The side's REST descriptor reports the declared
`guard_model` and `guard_model_applied`, the envelope the arm guard checks
the side with. The guard knows `d1/parallel_gripper` only, which is also its
default: every other id, and a descriptor that declares none, is checked
with the default envelope, and `guard_model_applied` differs from
`guard_model` to say so. The daemon's guard model is one compiled-in robot
description; an envelope for a new end effector is added to the daemon (its
capsules in that description and its id in the guard's envelope catalog),
not delivered over this contract.

**Liveness.** The side is **available** while the accepted provider
instance's newest heartbeat is younger than the side's stale threshold
(`[end_effector.<side>] stale_after_ms`, 100 to 5000, default 500) and names
the accepted generation. Otherwise every `set` and `joints` is refused with
`unavailable` (HTTP 502), and `GET /v1/end_effectors/{side}` answers
`fitted: true`, `available: false`, `state: null`, the accepted descriptor
(or `null` before one), and the reason in `error`: no provider announced,
the provider's descriptor refused, no heartbeat for N ms, or the services
not open. A state older than the threshold is served with `live: false`.

A side whose flange channel is relayed (`flange_bus = true`) is driven
through a device its provider addresses on that channel, so it is not
available either while the accepted declaration's `node_id` is `-1`: its
`error` is the provider's (the fault of its newest state), and every command
but `stop` is refused `unavailable`.

**The command ceiling.** The daemon never sends `set` or `joints` faster
than the descriptor's `max_command_hz`, counted over both together: a `set`
waits for its slot; a `joints` target that arrives inside a slot replaces
the one waiting for it, and the newest leaves when the slot opens (stamped
then, so the provider does not age it out). `stop` is never limited.

**The stop and the soft kill.** A stop (`POST /v1/end_effectors/{side}/stop`,
or `POST /v1/soft_kill` for both sides) raises the side's stop generation
and publishes `control` at once, drops a waiting `joints` target, and then
sends a `stop` request and waits up to 2 s for its answer. On an absent
provider it answers `unavailable` naming the control topic; a provider that
returns takes the current generation as its baseline (a stop is never
replayed to it), and while the soft-kill latch stands the daemon sends it
nothing that moves. Under the soft-kill latch the daemon refuses
`set` and `joints` before anything reaches the wire; `stop`, `clear_fault`,
`registers` and reads stay reachable. The arm lease does not arbitrate
end-effector commands.

**The hold.** A hold (`POST /v1/end_effectors/{side}/hold`) is sent as a
`set` with `extra` `{"hold": true}` and `openness` `0.0` to a provider that
lists `hold` in `set_extra`, under the soft kill's gate like any `set`; for a
side whose provider does not list it the daemon sends nothing and answers
that nothing was held (`{"held": false}`), leaving that provider's behaviour
as it was.

**The home.** A home (`POST /v1/end_effectors/{side}/home`) is sent as a
`set` with `extra` `{"home": true}` and `openness` `0.0` to a provider that
lists `home` in `set_extra`, under the soft kill's gate; for a provider that
does not list it but declares `openness`, the daemon sends an ordinary
`set` to openness `1.0` (open); for one that declares neither, it sends
nothing and answers that nothing was homed.

**Restarts.** A provider restart is a new `instance_id`: the daemon forgets
the old instance's state, waits for the new instance's descriptor, and
answers requests still in flight to the old one `unavailable`. A daemon
restart is a new daemon `instance_id`: the provider keeps serving; the
daemon's subscribers receive the latched descriptor on the provider's next
republish, and the side becomes available again within one descriptor
period. Nothing is replayed in either direction: `joints` has no history,
and a `set` cannot outlive its start deadline.

## 6. Versioning

- Any change to a layout, a code, a bit or a service setting is a new major
  version: `end_effector.shm/2`, type names `omakase_ee_v2_*`, a new
  `1.layout.json` sibling (`2.layout.json`), and `schema_version` 2. The
  type names keep the two majors from opening each other's services; the
  `schema_version` check refuses a message whose sender stamps a version it
  was not built for.
- Version 1 is frozen. The SHA-256 of `1.layout.json` is
  `30414fd5c321b72ee171a14edb56fca3ac2fa19b25881454383fc9a160f5dfee`; the
  contract's Rust crate pins it (`LAYOUT_SHA256`), and a provider that
  vendors the file SHOULD pin it too, so a change on either side fails a
  test there instead of drifting.
- A `detail` is versioned by the major of its own schema id
  (`detail.schema`) and never by this contract: a provider of a new device,
  with a new schema id, needs no change here or in the daemon.

## 7. Conformance checklist for a provider

1. Runs as the daemon's account; builds its node from the default iceoryx2
   configuration with the root and prefix of §1; iceoryx2 0.9.3.
2. Opens the eight services of its base with the settings of §2, as
   publisher of `descriptor`, `heartbeat`, `state`, `tick`, subscriber of
   `joints` and `control`, and server of `command` and `fault`.
3. Defines each message with exactly the layout of `1.layout.json`
   (checking its own definitions, and the file's SHA-256, against that file
   in a test) and the type names it lists.
4. Draws a non-zero random `instance_id` per start; stamps `schema_version`
   1, a strictly increasing `seq` per service and `CLOCK_MONOTONIC` in every
   header.
5. Follows the rules of §4.

## 8. A worked example

A third party's two-finger gripper on the right arm, its driver in Python:

1. The robot's daemon configuration declares the side:

   ```toml
   [end_effector.b]
   driver = "shm"                 # served by its own process
   model = "acme/two-finger-g2"   # optional: refuse any other model
   # shm_service = "omakase/ee/b" # the default
   # stale_after_ms = 500         # the default
   ```

2. The provider runs as a unit of its own:

   ```ini
   [Unit]
   Description=ACME gripper provider (end_effector.shm/1)
   After=d1-firmwared.service

   [Service]
   User=doraemon
   ExecStart=/opt/acme/bin/acme-gripper-provider --service omakase/ee/b
   Restart=on-failure
   RestartSec=1s

   [Install]
   WantedBy=multi-user.target
   ```

3. At start it opens its device, draws its instance id, opens the eight
   services under `/run/d1-firmwared/iceoryx2/` with prefix `omakase_ee_`,
   and announces: `driver = "acme-gripper"`, `detail_schema = "acme.report/1"`,
   `model = "acme/two-finger-g2"`, one joint `jaw` in rad over `[0, 0.08]`,
   capabilities `openness | joints | stroke_completion | joint_velocity`,
   `grip_presets = soft | firm`, `max_command_hz = 100`, a tool of 0.45 kg
   with its centre of mass 40 mm and its tool centre point 110 mm along the
   flange's Z axis, and `guard_model = "acme/two-finger-g2"`. It publishes a
   heartbeat every 50 ms and a state every 20 ms with the jaw's position and
   velocity and its own report as `detail`.
4. `GET /v1/end_effectors/b` now answers `available: true` and the
   descriptor, with the declared `tool`, `guard_model: "acme/two-finger-g2"`
   and `guard_model_applied: "d1/parallel_gripper"` (the guard has no
   envelope of that id). The daemon has registered the tool on arm B:
   `GET /v1/arm/b/tool` reads `source: "config"`, `model:
   "acme/two-finger-g2"` and the declared values. `POST /v1/end_effectors/b/set {"openness": 0.0, "grip":
   "firm"}` reaches the provider as a `CommandRequest` with `op` 1, grip 1
   and the wait bit; it closes, answers `ok` when the stroke concludes, and
   the client's request answers `null`.
5. The provider crashes: within 500 ms the side reads `available: false`
   with "no heartbeat for … ms". systemd restarts it; it announces the same
   declaration under a new instance id and the side is available again.
6. An operator's soft kill: the provider sees `stop_generation` rise and the
   `stop` request, disables its motor without opening, and answers `ok`.
