# `flange_bus.shm/1` — an arm side's flange CAN channel, relayed to a provider

**Contract version:** 1 (`schema_version` 1). **Transport:** iceoryx2
`=0.9.3`. **Byte layout:** `1.layout.json` beside this file, which is
normative for every offset, size, code and service setting; the tables below
mirror it and a test fails when they drift apart. **Rust definitions:**
module `flange` of crate `d1fw-ee-shm-contract`. **Daemon side:**
`d1-firmwared`'s flange relay; for a provider's tests, `Host` of crate
`d1fw-ee-harness` applies the same gates. **Provider SDK (Rust):** `FlangeBus`
in crate `d1fw-ee-provider`.

An end effector bolted to a D1 arm's flange talks over that arm's end-module
CAN channel, which the arm controller relays and which only `d1-firmwared`
(the **daemon**) can reach. This contract lets the device's driver run in a
process of its own — a **provider**, the same process that serves the side
over `end_effector.shm/1` — by relaying the channel through shared memory:
the daemon publishes every frame it receives, and puts the provider's frames
on the channel.

The daemon keeps the channel. It sends a provider's frame only while that
provider's heartbeat is fresh, within the side's frame size and tx rate
ceiling, and — for a frame that can move the device — only while the end
effectors' soft-kill latch is released. It knows nothing about the device:
which frame does what is the provider's declaration, made per frame (§3.4).

The relay is a process boundary, not a security boundary. The provider runs
as the daemon's account (§1.3), which can open the daemon's shared memory
and could forge anything this contract carries. The gates of §5 contain a
provider that is wrong (stale, too fast, still streaming when the latch
rises, crashed), not one that is hostile.

The key words MUST, MUST NOT, SHOULD and MAY are to be read as in RFC 2119.

## 1. Transport and root

1. Every participant MUST be built against iceoryx2 `0.9.3` exactly.
2. Every participant MUST build its iceoryx2 node from iceoryx2's default
   configuration with the root and prefix of `end_effector.shm/1` §1
   (`global.root-path` `/run/d1-firmwared/iceoryx2/`, `global.prefix`
   `omakase_ee_` on a robot; the daemon's `[end_effector] shm_root_path` and
   `shm_prefix`).
3. A provider MUST run as the account the daemon runs as, for the reason
   `end_effector.shm/1` §1.3 gives (iceoryx2 0.9.3 creates every resource
   owner-only); the daemon's package ships the unit template
   `d1-firmwared-ee-provider@.service` for that.

## 2. Services

A side's flange channel is bound by the base `omakase/flange/<side>`
(`a` or `b`). The daemon and the provider MUST open every service with the
settings below; either may create it first. Every user header is `()`.

| service | pattern | payload | writer | history | buffer | safe overflow | max writers | max readers |
| --- | --- | --- | --- | ---: | ---: | --- | ---: | ---: |
| `<base>/rx` | pub/sub | `RxFrame` | daemon | 0 | 64 | true | 1 | 2 |
| `<base>/tx` | pub/sub | `TxFrame` | provider | 0 | 64 | true | 1 | 1 |
| `<base>/status` | pub/sub | `Status` | daemon | 1 | 2 | true | 1 | 4 |
| `<base>/heartbeat` | pub/sub | `Heartbeat` | provider | 1 | 2 | true | 1 | 4 |

Every topic admits one writer, so one side has one relay (one daemon) and
one provider: a second provider cannot create its `tx` or `heartbeat`
publisher, and a second daemon cannot create its `rx` publisher. `tx` admits
one reader, the daemon.

## 3. Messages

The conventions are those of `end_effector.shm/1` §3: `#[repr(C)]`,
little-endian, explicit `reserved` fields written 0 and ignored, no implicit
padding, NUL-padded UTF-8 text, a flag word that sets an undefined bit is
refused, and every message starts with the 32-byte `Header` (the same
layout as `end_effector.shm/1`'s: `schema_version`, `instance_id` drawn once
per process start, `seq` strictly increasing per sender and service from 1,
`mono_ns` from `CLOCK_MONOTONIC`). `schema_version` is 1 of **this**
contract. The type names carry this contract's major (`omakase_flange_v1_*`).

### 3.2 Codes and bits

| field | values |
| --- | --- |
| `Frame.flags` | bit 0 `extended_id` (a 29-bit identifier) |
| `TxFrame.kind` | `0` motion, `1` read, `2` stop |
| `Status.flags` | bit 0 `channel_up`, 1 `latched`, 2 `arm_faulted` |
| `Status.channel_flags` | bit 0 `suppresses_repeats`, 1 `extended_ids` |

### 3.3 What each message means

**`Frame`**: one CAN or CAN FD frame. `id` is an 11-bit identifier (at most
`0x7FF`), or a 29-bit one (at most `0x1FFFFFFF`) with `extended_id`. `len`
is the payload length, 0 to 64; the bytes of `data` past it are zero. A
payload of a length CAN FD does not have (9 to 11, 13 to 15, …) is padded
with zeros to the next one on the wire; the device reads its own length
field, as it does from every other sender.

**`RxFrame`** (daemon, as it happens): a frame the daemon took off the
channel at `channel_mono_ns`, published whether or not a provider is bound.
The D1 arm controller's passthrough has reported a received identifier in
either byte order, so the daemon reads it little-endian when that value is
an identifier the channel carries and big-endian otherwise, and takes the
first 64 bytes of a payload reported longer than that.
The `rx` stream is best effort and newest-kept: a reader that falls behind
loses the oldest frames, and a gap in the header `seq` counts them.

**`TxFrame`** (provider): a frame to put on the channel, and `kind`, what
it does to the device:

- `motion` (0): it can move the device — a target, an enable, a mode or a
  parameter write. The zero value, so an unset field is the most restricted
  kind.
- `read` (1): it reads and commands nothing — a poll, a register read.
- `stop` (2): it takes the actuators' authority away and never moves the
  device — a disable. A stop that would open a gripper is `motion`.

**`Heartbeat`** (provider, at least every 100 ms): the provider is alive.

**`Status`** (daemon, latched, every 100 ms and whenever its binding, the
latch, the arm fault, the channel or `tx_seq_seen` changes): `bound_instance_id` is the
provider whose frames the relay takes (0: none); `tx_seq_seen` the newest tx
`seq` of that provider the relay has taken, sent or refused. `channel_up`:
the channel's newest operation (a send, or a receive) succeeded; otherwise
`channel_error` says why. `latched`: motion frames are refused.
`arm_faulted`: the arm controller that carries the channel reports a fault
on the channel's arm side (a nonzero error code, or its error mode); while
it does, frames the provider sends may not reach the device although
frames from the device still arrive (seen on a D1 when the controller
reported `PdoAbnormal` / `BusTopologyAbnormal`: a gripper's position
commands stopped landing while its status replies kept coming).
`channel_flags` say what the channel is: `suppresses_repeats` — it hands
over a received frame only when its bytes differ from the frame it handed
over last (the D1 arm's end module, measured on arm A 2026-08-13), so a
device asked the same question twice is heard once; `extended_ids` — it
carries 29-bit identifiers (the D1 end module, as the daemon drives it,
carries 11-bit ones only). `max_tx_hz` and `max_frame_len` are the relay's
ceilings. The counters run from the daemon's start: `rx_frames` published,
`tx_forwarded` sent, and every refusal by its reason (§5).

## 4. Rules a provider MUST follow

1. Serve the side over `end_effector.shm/1` as well, as one process: the
   flange relay exists for the provider of the side's end effector.
2. Publish its heartbeat at least every 100 ms, from start to exit.
3. Label every tx frame with its kind truthfully (§3.3). A frame whose
   effect it does not know is `motion`.
4. Keep at most 32 tx frames published beyond the newest status's
   `tx_seq_seen` while it is the bound instance, so the `tx` topic (buffer
   64) never overwrites a frame the relay has not read.
5. Send nothing while it is not the bound instance, and no motion frame
   while the status says `latched`: the relay refuses them (§5), and the
   device driver should fail the command at once instead of waiting for an
   answer that cannot come.
6. Pace its frames to `max_tx_hz`; the relay refuses the excess.
7. Treat `rx` as lossy: match every answer to its question, and expect
   frames that answer someone else (an echo, a late answer to a question
   given up on).
8. When `suppresses_repeats` is set, never rely on a second identical
   answer arriving: vary the question (another register length, another
   poll type) or interpose a different exchange.
9. While the status says `arm_faulted`, do not rely on a command reaching
   the device. A device whose motion depends on its commands landing
   starts none and settles what is in progress: the stock gripper
   provider halts a stroke at the measured jaws, refuses new strokes, and
   keeps a standing hold at its current cap.

## 5. What the daemon does

**Binding.** The relay binds the sender of the newest heartbeat whose header
`mono_ns` is younger than the side's stale threshold
(`[end_effector.<side>] stale_after_ms`, default 500) and unbinds it when its
heartbeat gets older. A provider that restarts is a new instance: the relay
binds it on its first heartbeat.

**The gates.** For every tx frame, in this order, the relay refuses and
counts:

1. `tx_refused_invalid` — a frame that does not decode (§3), a `len` over
   the channel's `max_frame_len`, or an `extended_id` the channel does not
   carry;
2. `tx_refused_unbound` — a sender that is not the bound instance;
3. `tx_refused_stale` — a frame whose header `mono_ns` is more than 100 ms
   old when the relay takes it: a frame delayed that long is not sent late;
4. `tx_refused_latched` — a `motion` frame while the end effectors'
   soft-kill latch stands (`POST /v1/soft_kill` latches it; it stands
   until released), and from the relay's start until the daemon has wired
   the latch to it. `read` and `stop` frames pass, so a provider can still
   read its device, and stop it, under a soft kill;
5. `tx_refused_rate` — a `motion` or `read` frame beyond the side's tx rate
   ceiling (`[end_effector.<side>] flange_max_tx_hz`, default 1000 frames
   per second, a token bucket holding 50 ms of frames). `stop` frames are
   never refused by the ceiling.

What passes is put on the channel in `tx` order (`tx_forwarded`); a send the
channel fails is `tx_failed` and turns `channel_up` off until a send or a
receive succeeds again. A gap in a bound
provider's `seq` is `tx_lost`. The relay sends no frame of its own and never
alters one.

**Why the latch admits reads and stops.** Under a soft kill the daemon stops
the side's end effector through `end_effector.shm/1` (its stop generation
and its `stop` request), and the provider's stop is a frame on this
channel; refusing it would leave the device under authority. A read moves
nothing, and `end_effector.shm/1` keeps reads reachable under the latch.

**The arm fault.** The daemon sets `arm_faulted` from the arm feedback it
already receives (the same reading `GET /v1/arm/{side}/state` reports), and
publishes the change within one relay pass (1 ms) of that feedback. The
relay refuses nothing because of it: what a device should do while its
commands may not land is the provider's to decide (§4, rule 9).

**What the relay does not do.** It does not stop the device when the
provider dies or goes silent: it has no device knowledge, and the device
keeps its last command. The side's `end_effector.shm/1` resource turns
unavailable, every command is refused, and the next provider instance takes
the current stop generation as its baseline.

**Latency.** The daemon takes tx frames at least every millisecond and
publishes a received frame as soon as the channel hands it over; the Rust
SDK reads `rx` at least every half millisecond. On an idle host a frame
reaches the channel within about 1 ms of the provider's send, and an answer
reaches the provider within about 1 ms of the channel delivering it: a
request-answer exchange costs a provider about 2 ms more than an in-process
driver paid, on top of the arm controller's own relay. The path is not real
time; a loop that needs sub-millisecond reaction does not belong behind it.

## 6. Versioning

- Any change to a layout, a code, a bit or a service setting is a new major
  version: `flange_bus.shm/2`, type names `omakase_flange_v2_*`, a
  `2.layout.json` sibling, and `schema_version` 2.
- Version 1 is frozen. The SHA-256 of `1.layout.json` is
  `43d74ebf4944cf21c40e368cf6816ef0bc71698a5b2fe34988d8dfe12bf766b7`; the
  contract's Rust module pins it (`flange::layout::LAYOUT_SHA256`), and a
  provider that vendors the file SHOULD pin it too.
- The contract versions independently of `end_effector.shm/1`.

## 7. Conformance checklist for a provider

1. Runs as the daemon's account; builds its node with the root and prefix
   of §1; iceoryx2 0.9.3.
2. Opens the four services of its side with the settings of §2, as
   publisher of `tx` and `heartbeat` and subscriber of `rx` and `status`.
3. Defines each message with exactly the layout of `1.layout.json` and the
   type names it lists, and checks the file's SHA-256 in a test.
4. Draws a non-zero random `instance_id` per start; stamps `schema_version`
   1, a strictly increasing `seq` per service and `CLOCK_MONOTONIC` in every
   header.
5. Follows the rules of §4.

## 8. A worked example

The LinkerHand O30 on arm A, served by `d1-ee-linkerbot-provider` (package
`d1-ee-linkerbot`):

1. The daemon's configuration declares the side:

   ```toml
   [end_effector.a]
   driver = "shm"
   model = "linkerbot/o30"
   flange_bus = true
   ```

2. `/etc/d1-firmwared/ee-provider/a.env` holds
   `EE_PROVIDER_COMMAND=/opt/d1-ee-linkerbot/bin/d1-ee-linkerbot-provider --side a`,
   and `systemctl enable --now d1-firmwared-ee-provider@a` starts it.
3. The provider opens `omakase/flange/a`, publishes its heartbeat, and
   waits for a status that names it bound with the channel up. The status
   says `suppresses_repeats`, so its HOP reads ask for one byte more than the
   previous answer had.
4. It probes ids 1 to 15 with `read` frames (the error-record register),
   finds the hand at id 2, and announces itself over `end_effector.shm/1`
   with `node_id` 2, twenty fraction joints and its tool.
5. `POST /v1/end_effectors/a/set {"openness": 0.0}` reaches it as a `set`;
   it sends the control-mode and joint-enable writes as `motion`, reads the
   stored masks back as `read`, and the bending-group targets as `motion`.
6. `POST /v1/soft_kill`: the latch rises, the provider's stop sends the
   joint-disable write as `stop`, which passes; a joint target it was still
   sending is `motion` and is refused (`tx_refused_latched`).
