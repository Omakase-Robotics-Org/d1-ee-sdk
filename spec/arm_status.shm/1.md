# `arm_status.shm/1` — the daemon's view of the arms

**Contract version:** 1 (`schema_version` 1). **Transport:** iceoryx2
`=0.9.3`. **Byte layout:** `1.layout.json` beside this file, which is
normative for every offset, size, code and service setting; the tables below
mirror it and a test fails when they drift apart. **Byte layout SHA-256:**
`c7d6685594206be6d58ed7d7f28fe5701eaf3818dc7d40d45156143c621868fb`. **Rust definitions:** crate `d1fw-arm-shm-contract`. **Daemon
side:** `d1-firmwared`'s arm publisher (`[arm] shm_publish`).

`arm_feedback.shm/1` carries what the arm controller reports. This contract
carries what the daemon (`d1-firmwared`) itself holds about the arms and no
controller record shows: the soft-kill latch, the arm lease and its holder,
the brakes it released, the tool it registered, the trajectory lane, the
freshness of the feedback, and the counters of the `arm_command.shm/1`
command path. It is latched: a reader that starts gets the newest status at
once.

The key words MUST, MUST NOT, SHOULD and MAY are to be read as in RFC 2119.

## 1. Transport and root

As `arm_feedback.shm/1` §1: iceoryx2 `0.9.3`, the end effectors' root and
prefix, a reader running as the daemon's account.

## 2. Services

The base is `omakase/arm` (the daemon's default).

| service | pattern | payload | writer | reader | history | buffer | safe overflow | max writers | max readers |
| --- | --- | --- | --- | --- | ---: | ---: | --- | ---: | ---: |
| `<base>/status` | pub/sub | `Status` | daemon | reader | 1 | 2 | true | 1 | 8 |

### 3.2 Codes and bits

| name | value | meaning |
| --- | ---: | --- |
| `MODE_UNKNOWN` | 0 | `SideStatus.mode`: a controller state the daemon does not know |
| `MODE_IDLE` | 1 | idle (servos off) |
| `MODE_POSITION` | 2 | joint position mode |
| `MODE_PVT` | 3 | PVT mode |
| `MODE_TORQUE` | 4 | torque, impedance or force-compliance mode |
| `MODE_RELEASE` | 5 | released (floating) |
| `MODE_ERROR` | 6 | the controller reports an error: a protective stop |
| `SIDE_BRAKES_RELEASED` | 1 | `SideStatus.flags` bit: the daemon holds this arm's brakes released for hand guiding |
| `SIDE_PROTOCOL_MISMATCH` | 2 | the controller's firmware family contradicts the configured protocol (motion refused) |
| `SIDE_STATIONARY` | 4 | the controller reports the arm stationary |
| `TOOL_NONE` | 0 | `SideStatus.tool_source`: nothing registered since the daemon started |
| `TOOL_CONFIG` | 1 | the tool the side's configured end effector declares |
| `TOOL_CLIENT` | 2 | a client's `POST /v1/arm/{side}/tool` |
| `STATUS_SOFT_KILLED` | 1 | `Status.flags` bit: the arm soft-kill latch stands; every motion command is refused |
| `STATUS_LEASE_HELD` | 2 | a live arm lease is held (`lease_*` describe it) |
| `STATUS_COMMAND_SERVED` | 4 | the `arm_command.shm/1` path is served |
| `STATUS_FEEDBACK_STALE` | 8 | the newest controller record is older than `feedback_stale_after_ms` |
| `STATUS_STREAM_STOPPED` | 16 | the `arm_command.shm/1` stream is stopped: its newest command was refused |
| `TRAJECTORY_NONE` | 0 | `Status.trajectory_phase`: no job since the daemon started |
| `TRAJECTORY_RUNNING` | 1 | playback in progress |
| `TRAJECTORY_COMPLETED` | 2 | playback ran to the end |
| `TRAJECTORY_CANCELLED` | 3 | playback was cancelled |
| `TRAJECTORY_FAILED` | 4 | playback stopped on an error |

### 3.3 What each field means

**`Status`**:

- `feedback_seq`: the header `seq` of the newest `arm_feedback.shm/1`
  sample, so a reader of both can line them up; `feedback_age_ns`: how old
  the newest controller record was when this status was published
  (`u64::MAX` before the first).
- `feedback_stale_after_ms`: the silence after which the daemon calls the
  arm's facts stale (its idle poll interval times its stale count; `0` when
  the poll is disabled and silence is normal), and `STATUS_FEEDBACK_STALE`
  whether it is so now.
- `lease_*`: the arm lease as `GET /v1/arm/lease` reports it — holder,
  class rank (`10` ambient, `50` policy, `90` operator), grant epoch and
  whole seconds to expiry. Never its token.
- `commands_*`, `max_command_hz`, `STATUS_COMMAND_SERVED`,
  `STATUS_STREAM_STOPPED`: the `arm_command.shm/1` path — commands written,
  refused and superseded since the daemon started, its rate ceiling (`0`
  while it is not served), and whether its stream is stopped.
- `trajectory_id`, `trajectory_phase`: the newest job of the daemon's
  trajectory lane (`POST /v1/arm/trajectory/start`).
- `period_ms`: how often the status is published when nothing changes.

**`SideStatus`**, arm A (index 0) and arm B (index 1): the arm's mode and
error as the daemon reads them from the newest record, whether it is
stationary, the daemon's brake record, the controller's frame-miss counters,
and the tool the daemon registered on the arm (where it came from, and its
mass; NaN while none is registered). The tool's name is not carried: the
daemon does not interpret what an end effector is.

## 4. Rules a reader MUST follow

1. Open the service with the settings of §2 as a subscriber, and never
   publish on it.
2. Check `schema_version`; a change of the header `instance_id` is a
   restarted daemon.
3. Treat a status older than three periods (`period_ms`, by its header
   `mono_ns`) as a daemon that is not publishing.

## 5. What the daemon does

It publishes a status every `period_ms` (100 ms), and at once when the arm
soft-kill latch moves. The values are read when the status is built: the
latch and the lease from the daemon's own records, the modes from the
newest controller record, the counters from the command path.

## 6. Versioning

- Any change to a layout, a code, a bit or a service setting is a new major
  version: `arm_status.shm/2`, type names `omakase_arm_status_v2_*`, a
  `2.layout.json` sibling, and `schema_version` 2.
- Version 1 is frozen. The SHA-256 of `1.layout.json` is
  `c7d6685594206be6d58ed7d7f28fe5701eaf3818dc7d40d45156143c621868fb`; the crate pins it
  (`layout::STATUS_LAYOUT_SHA256`), and the daemon pins it again in its own
  tests.

## 7. Conformance checklist for a reader

1. Runs as the daemon's account; builds its node with the root and prefix
   of `arm_feedback.shm/1` §1; iceoryx2 0.9.3.
2. Opens `<base>/status` with the settings of §2 as a subscriber.
3. Defines `Status` and `SideStatus` with exactly the layout of
   `1.layout.json` and the type names it lists, and checks the file's
   SHA-256 in a test.

## 8. A worked example

A supervisor that stops streaming when the robot is soft-killed or its
lease is gone subscribes to `omakase/arm/status`, and on every sample checks
`flags & STATUS_SOFT_KILLED` and whether `lease_holder` is still its own
name with its own `lease_epoch`; a higher epoch under its name means it was
displaced and granted the lease again, so whatever it believed about the
arms is stale.
