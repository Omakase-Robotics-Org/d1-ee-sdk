# `arm_feedback.shm/1` — every arm controller feedback record, as it arrives

**Contract version:** 1 (`schema_version` 1). **Transport:** iceoryx2
`=0.9.3`. **Byte layout:** `1.layout.json` beside this file, which is
normative for every offset, size, code and service setting; the tables below
mirror it and a test fails when they drift apart. **Byte layout SHA-256:**
`f9bbac48eff4d24449d66f0219ee32960ecf58cf39aebc4d49b522909758b65a`. **Rust definitions:** crate `d1fw-arm-shm-contract` (modules
`wire`, `names`, `ports`, `layout`). **Daemon side:** `d1-firmwared`'s arm
publisher (`[arm] shm_publish`).

The D1's two arms are driven by one arm controller, which sends the daemon
(`d1-firmwared`) a feedback datagram — the 1428-byte dual-arm state record
(`DCSS`) behind a two-byte `FX` tag — about every millisecond. This contract
publishes every one of those records to any process on the robot, the moment
the daemon receives it: each field decoded, both arms, and the record itself
byte for byte, so that a reader (a ROS 2 bridge, a recorder, an external
controller) sees everything the daemon sees, at the rate the daemon sees it,
without asking the daemon for anything.

The contract only publishes. Commanding the arms is `arm_command.shm/1`;
the daemon's own view of them (mode, lease, latch) is `arm_status.shm/1`;
what happens to them is `arm_events.shm/1`.

The key words MUST, MUST NOT, SHOULD and MAY are to be read as in RFC 2119.

## 1. Transport and root

1. Every participant MUST be built against iceoryx2 `0.9.3` exactly.
2. Every participant MUST build its iceoryx2 node from iceoryx2's default
   configuration with the root and prefix of `end_effector.shm/1` §1
   (`global.root-path` `/run/d1-firmwared/iceoryx2/`, `global.prefix`
   `omakase_ee_` on a robot; the daemon's `[end_effector] shm_root_path` and
   `shm_prefix`). The arm services share that root with the end-effector
   services.
3. A reader MUST run as the account the daemon runs as: iceoryx2 0.9.3
   creates every resource readable and writable by its owner only.
4. The daemon publishes from an `ipc_threadsafe` service; a reader opens the
   same service with either variant (`ipc` or `ipc_threadsafe`), which share
   one shared-memory layout.

## 2. Services

The service names are the base `omakase/arm` (the daemon's default) followed
by `/` and the suffix. The daemon and a reader MUST open the service with
the settings below; either may create it first. The user header is `()`.

| service | pattern | payload | writer | reader | history | buffer | safe overflow | max writers | max readers |
| --- | --- | --- | --- | --- | ---: | ---: | --- | ---: | ---: |
| `<base>/feedback` | pub/sub | `Feedback` | daemon | reader | 1 | 256 | true | 1 | 8 |

One writer, the daemon. A buffer of 256 holds a quarter second of records at
1 kHz, so a reader that takes its samples every few milliseconds loses none;
history 1 hands a reader that starts the newest record on the next publish.

## 3. Messages

The conventions are those of `end_effector.shm/1` §3: `#[repr(C)]`,
little-endian, explicit `reserved` fields written 0 and ignored, no implicit
padding, NUL-padded text, and every message starts with the 32-byte `Header`
(`schema_version`, `instance_id` drawn once per daemon start, `seq` strictly
increasing from 1, `mono_ns` from `CLOCK_MONOTONIC`). `schema_version` is 1
of **this** contract. The type names carry this contract's major
(`omakase_arm_feedback_v1_*`); the header keeps the shared
`omakase_ee_v1_Header`.

Every value the controller reports is carried in the controller's own type
(`f32`, `i32`, `i16`, `u8`) and its own unit, unconverted.

### 3.2 Codes and bits

| name | value | meaning |
| --- | ---: | --- |
| `PROTOCOL_UNKNOWN` | 0 | `Feedback.protocol`: not known |
| `PROTOCOL_FX` | 1 | the `FX` command frame (controller firmware up to 100341) |
| `PROTOCOL_FY` | 2 | the `FY` command frame (controller firmware from 100343) |
| `FEEDBACK_PROTOCOL_MISMATCH` | 1 | `Feedback.flags` bit: the controller's firmware family contradicts the configured protocol; the daemon refuses every motion command |
| `FEEDBACK_RAW_TRUNCATED` | 2 | `Feedback.flags` bit: the record was longer than `raw` and `raw` holds its first bytes |
| `RAW_DCSS_1428` | 1 | `Feedback.raw_format`: the controller's 1428-byte dual-arm state record, as it follows the `FX` tag |
| `STATE_IDLE` | 0 | `SideFeedback.cur_state`: idle (servos off) |
| `STATE_POSITION` | 1 | position mode |
| `STATE_PVT` | 2 | PVT mode |
| `STATE_TORQUE` | 3 | torque (impedance, force) mode |
| `STATE_RELEASE` | 4 | released (floating) |
| `STATE_ERROR` | 100 | error: the controller's protective stop |
| `STATE_TO_POSITION` | 101 | transitioning to position |
| `STATE_TO_PVT` | 102 | transitioning to PVT |
| `STATE_TO_TORQUE` | 103 | transitioning to torque |
| `STATE_TO_RELEASE` | 104 | transitioning to released |
| `STATE_TO_IDLE` | 109 | transitioning to idle |

`cur_state` carries any other value the controller reports unchanged.

### 3.3 What each field means

**`Feedback`**, one per record the daemon received, in the order received:

- `rx_mono_ns`: `CLOCK_MONOTONIC` when the daemon received the record; the
  header `mono_ns` is when it published the sample, so `mono_ns -
  rx_mono_ns` is the daemon's publish delay and a reader's receive time minus
  `rx_mono_ns` is its whole delay.
- `controller_version`: the controller firmware version the daemon read at
  startup (`0` until it has).
- `protocol`, `flags`: the command frame the daemon speaks and whether the
  controller's family contradicts it.
- `para_*`: the controller's parameter-reply slot. It is one slot shared by
  every parameter read and write the daemon makes (including its idle
  feedback poll), so a value belongs to the parameter command whose serial
  `para_ret_serial` echoes; on a refusal the controller answers
  `error_code * 100 + serial`.
- `sides`: arm A (index 0, the physical left arm) and arm B (index 1).
- `raw`, `raw_len`, `raw_format`: the record itself, byte for byte. A field
  this contract does not decode (the controller's tag and PVT words among
  them) is read from here, at the controller's own offsets.

**`SideFeedback`**, one arm, field by field from the controller's records
(`StateCtr`, the input record `RT_IN`, the output record `RT_OUT`):

| field | controller field | unit |
| --- | --- | --- |
| `cur_state`, `cmd_state`, `error_code` | `StateCtr.m_CurState`, `m_CmdState`, `m_ERRCode` | code |
| `imp_type` | `RT_IN.m_ImpType` (`1` joint, `2` Cartesian, `3` force impedance) | code |
| `out_frame_serial`, `in_frame_serial` | `RT_OUT.m_OutFrameSerial`, `RT_IN.m_InFrameSerial` | count |
| `sys_cyc` | `RT_IN.m_SysCyc` (modulo 1 000 000) | cycles |
| `frame_miss_count`, `max_frame_miss_count` | `RT_IN.m_FrameMissCnt`, `m_MaxFrameMissCnt`: host command frames the controller did not receive, refreshed every 200 cycles; the vendor's healthy band is below 20 | count |
| `sys_cyc_miss_count`, `max_sys_cyc_miss_count` | `RT_IN.m_SysCycMissCnt`, `m_MaxSysCycMissCnt`: the controller's own missed realtime cycles | count |
| `vel_ratio`, `acc_ratio` | `RT_IN.m_Joint_Vel_Ratio`, `m_Joint_Acc_Ratio` | percent |
| `cart_kd_type`, `force_fb_type`, `force_type` | `RT_IN.m_Cart_KD_Type`, `m_Force_FB_Type`, `m_Force_Type` | code |
| `tip_di` | `RT_OUT.m_TipDI` | bits |
| `low_speed` | `RT_OUT.m_LowSpdFlag`: nonzero while the arm is stationary | flag |
| `traj_state` | `RT_OUT.m_TrajState` | code |
| `pos`, `vel` | `RT_OUT.m_FB_Joint_Pos`, `m_FB_Joint_Vel`: measured | degrees, degrees/s |
| `pos_e` | `RT_OUT.m_FB_Joint_PosE` | controller unit |
| `cmd_echo` | `RT_OUT.m_FB_Joint_Cmd`: the command the controller echoes | degrees |
| `accepted_cmd` | `RT_IN.m_Joint_CMD_Pos`: the joint command the controller holds, the newest host target it took | degrees |
| `current` | `RT_OUT.m_FB_Joint_CToq` | controller unit |
| `torque` | `RT_OUT.m_FB_Joint_SToq`: joint sensor torque | N·m |
| `temperature` | `RT_OUT.m_FB_Joint_Them` | °C |
| `est_friction`, `est_friction_dot`, `est_force` | `RT_OUT.m_EST_Joint_Firc`, `m_EST_Joint_Firc_Dot`, `m_EST_Joint_Force`: the controller's estimates | controller unit |
| `est_cart_fn` | `RT_OUT.m_EST_Cart_FN`: estimated force and torque at the tool | controller unit |
| `joint_k`, `joint_d` | `RT_IN.m_Joint_K`, `m_Joint_D`: joint impedance in effect | controller unit |
| `cart_k`, `cart_d`, `cart_kn`, `cart_dn` | `RT_IN.m_Cart_K`, `m_Cart_D`, `m_Cart_KN`, `m_Cart_DN` | controller unit |
| `force_dir`, `force_pidul`, `force_adj_lmt`, `force_cmd` | `RT_IN.m_Force_Dir`, `m_Force_PIDUL`, `m_Force_AdjLmt` (mm), `m_Force_Cmd` (N) | as noted |

"Controller unit" marks a field whose unit the vendor's interface headers
do not state; it is carried exactly as reported. `cmd_echo` and
`accepted_cmd` together with `pos` are the commanded-versus-measured view
of each joint.

## 4. Rules a reader MUST follow

1. Open the service with the settings of §2 as a subscriber, and never
   publish on it.
2. Check `schema_version` and treat a change of the header `instance_id` as
   a restarted daemon (`seq` starts again from 1).
3. Count gaps in `seq` as records it did not receive: a reader that falls
   behind by more than 256 records loses the oldest ones. A reader that must
   see every record takes its samples at least every 200 ms.
4. Read a field this contract does not decode from `raw`, only while
   `raw_format` is a value it knows.

## 5. What the daemon does

**When it publishes.** For every feedback datagram it receives and accepts
(exactly 1430 bytes, tagged `FX`), on the receive path, before decoding the
record for its own use: the publisher writes each decoded field and the
record straight into a loaned shared-memory sample and sends it. Nothing is
published for a datagram it refuses.

**At what rate.** The controller's. It answers each host command datagram
with one feedback datagram until the first command datagram of its process
lifetime reaches it, then streams about 1000 per second for the rest of
that lifetime. The daemon's idle poll (a read-only parameter request every
`[arm] feedback_poll_ms`, 50 ms by default) makes that first contact at
startup, so on a running robot the topic carries about 1000 samples per
second. The simulated controller of `--backend sim` streams at
`[arm] sim_feedback_hz` (1000 by default).

**What it costs.** One sample of 3408 bytes per record. Measured in the
simulator on a workstation (release build, a reader spinning on its own
thread): receive-to-reader latency p50 3 µs, p99 14 µs at 1000 records per
second, no `seq` gap over 3000 records.

**Events.** A change of an arm's `cur_state` or `error_code`, and
`frame_miss_count` crossing 20 either way, are also published on
`arm_events.shm/1`.

## 6. Versioning

- Any change to a layout, a code, a bit or a service setting is a new major
  version: `arm_feedback.shm/2`, type names `omakase_arm_feedback_v2_*`, a
  `2.layout.json` sibling, and `schema_version` 2.
- Version 1 is frozen. The SHA-256 of `1.layout.json` is
  `f9bbac48eff4d24449d66f0219ee32960ecf58cf39aebc4d49b522909758b65a`; the crate pins it
  (`layout::FEEDBACK_LAYOUT_SHA256`), the daemon pins it again in its own
  tests, and a reader that vendors the file SHOULD pin it too.
- A new controller record format is a new `raw_format` value, which is a
  new major version.
- The contract versions independently of the other arm contracts and of
  `end_effector.shm/1`.

## 7. Conformance checklist for a reader

1. Runs as the daemon's account; builds its node with the root and prefix
   of §1; iceoryx2 0.9.3.
2. Opens `<base>/feedback` with the settings of §2 as a subscriber.
3. Defines `Feedback` and `SideFeedback` with exactly the layout of
   `1.layout.json` and the type names it lists, and checks the file's
   SHA-256 in a test.
4. Follows the rules of §4.

## 8. A worked example

A recorder logging both arms' commanded and measured joints:

1. It opens a node under `/run/d1-firmwared/iceoryx2/` with the prefix
   `omakase_ee_`, as the account `d1-firmwared` runs as, and subscribes to
   `omakase/arm/feedback`.
2. Every 5 ms it takes every sample waiting, and for each writes
   `header.seq`, `rx_mono_ns`, `sides[i].pos`, `sides[i].accepted_cmd` and
   `sides[i].frame_miss_count`.
3. A gap between two `seq` values is written as a loss; a new
   `instance_id` starts a new file.
